# Метро Москвы

[English](README.md) · Русский

**[metro.samoy.love](https://metro.samoy.love)** — офлайн-PWA для построения маршрутов
по московскому метро. Схема рисуется на канвасе по предрасчитанным координатам, маршрут
считается на устройстве — приложение целиком работает без сети.

## Зачем

Маршрут построит любое приложение метро. Хорошо нарисовать схему — почти никакое.

Схема метро — не карта. Это сознательная ложь о географии, рассказанная так, чтобы
человек на платформе прочитал её за три секунды. Правила этой лжи давние и вполне
конкретные: линии идут кратно 45°, кольца гладкие, станции одной пересадки сливаются
в общий узел, и каждая подпись обязана читаться, ничего не перекрывая.

Здесь эти правила и есть продукт. Маршрутизация — простая половина.

## Что здесь интересного

**Решатель геометрии на Go** — [`go-layout-solver/`](../go-layout-solver/), около 3400
строк. Выпрямляет линии до октолинейных углов, сглаживает кольца, разводит налезающие
станции. Его пороги выведены из констант самого рендерера
([`separation.go`](../go-layout-solver/separation.go)): оптимизатор считает в тех же
пикселях, в которых рисует канвас.

**Одна раскладка подписей на два рантайма.**
[`MetroMapLabelLayout.ts`](../src/components/MetroMapLabelLayout.ts) не зависит ни от
DOM, ни от React — измеритель текста инжектится (`ctx.measureText` в браузере, таблица
метрик в Node). Раньше было две копии, обязанные совпадать один в один, и проверить это
было нечем.

**Раскладка подписей как функция штрафа.** У наложения подписей, перекрытия станции и
пересечения линии свой явный вес, и соотношение между ними — и есть проектное решение
(см. [`QUALITY.md`](QUALITY.md)). Подбор соотношения снизил долю неразмещённых подписей
в плотном центре с 22.6% до 9.7%.

**Граф маршрутизации в 20 КБ.** Воркер собирается отдельным бандлом, поэтому импорт
полного графа продублировал бы около 123 КБ JSON;
[`routingGraphPayload.ts`](../src/metro/routingGraphPayload.ts) кодирует только рёбра.
Лежит он вне `assets/` намеренно: `vite-plugin-pwa` помечает этот каталог как
`revision: null`, и файл с фиксированным именем застрял бы в прекеше навсегда.

**Пиксельная визуальная приёмка в Docker.** `MetroMap.tsx` — 4700 строк отрисовки
канвасом, юнит-тестами её не увидеть. [`tools/visual-qa/`](../tools/visual-qa/) гоняет
настоящий Chromium против статик-сервера внутри контейнера — до хоста контейнер не ходит
вовсе — и падает при расхождении больше 0.1% кадра. Пропавший снимок засчитывается как
расхождение.

**CI проверяет дрейф, а не пороги.** Анализатор качества детерминирован, его отчёт
закоммичен, и задача сверяется с этим отчётом, а не с абсолютными числами. Сигнал,
который всегда красный, перестаёт быть сигналом.

**Обновление офлайн-приложения, которое ничего не ломает.** Ни `skipWaiting`, ни
`clientsClaim`: при `registerType: 'prompt'` новый service worker ждёт подтверждения,
потому что активация под уже загруженной страницей превращает её ленивые чанки в 404.

**Сторож CSS-переменных.** Однажды 283 использования `var(--space-*)` прожили с нулём
объявлений: `tsc`, ESLint, Vitest и сборка — всё зелёное, а приложение рисовалось вообще
без отступов. [`scripts/check-css-tokens.mjs`](../scripts/check-css-tokens.mjs) теперь
отдельный шаг CI.

**Встроенный редактор схемы.** `npm run dev:editor` открывает карту, где станции можно
таскать; сохранение пишет прямо в `data/` и заново запускает решатель, так что
перетаскивание в браузере оборачивается дифом в JSON-файле. Это отдельная точка входа, а
сторож [`scripts/check-prod-bundle.mjs`](../scripts/check-prod-bundle.mjs) следит, чтобы
она не попала в продакшн-бандл.

## Быстрый старт

```bash
npm install

npm run dev          # дев-сервер
npm run dev:pwa      # дев-сервер с включённым service worker
npm run dev:editor   # редактор схемы (editor.html)

npm run build        # tsc -b && vite build -> dist/
npm run preview      # предпросмотр продакшн-сборки

npm run lint
npm test             # Vitest (watch); в CI — npx vitest run
npm run e2e          # сквозные тесты по локальной прод-сборке
```

Сквозные тесты (Playwright, `e2e/`) проходят приложение так, как это делает человек.
`npm run e2e` сам собирает проект и поднимает `preview` — именно прод-сборку, потому что
service worker и precache в дев-режиме не существуют. Браузер ставится один раз:
`npx playwright install chromium`.

Покрыто: схема отрисовывается на канвасе (считаются непрозрачные пиксели — пустой канвас
в DOM выглядит так же, как полный) и перерисовывается при зуме; пара станций даёт маршрут
со временем, временем прибытия, пересадкой и перечнем станций по отрезкам; альтернативные
варианты переключаются; кнопка обмена меняет станции местами и пересчитывает; service
worker активируется, precache наполняется, и повторный заход **без сети** поднимает
приложение целиком со схемой; тема переключается, переживает перезагрузку и тянет за
собой `meta theme-color`.

Сквозная проверка во всех тестах: любая ошибка в консоли браузера и любой неудачный
сетевой запрос валят тест. Приложение, отдающее 200 с упавшим воркером маршрутов, здесь
красное — по коду ответа оно выглядело бы живым.

Смоук по живому сайту запускается отдельно и руками, в CI на PR не висит:

```bash
npm run e2e:prod                          # https://metro.samoy.love
E2E_PROD_URL=https://... npm run e2e:prod # другой адрес
```

Стенд визуальной приёмки (`tools/visual-qa`) — про другое: он снимает скриншоты настоящим
Chromium в Docker и сравнивает картинки. Сквозные тесты проверяют поведение, а не пиксели.

Пересборка данных и проверка качества схемы:

```bash
npm run build:data     # пересобрать normalized/fullGraph.json (нужен Go)
npm run quality        # анализ качества схемы -> normalized/quality_report.json
npm run quality:check  # то же, но с ненулевым кодом выхода при регрессе (для CI)
```

> **Важно:** UI не пересчитывает раскладку. Он использует готовые `layoutX/layoutY`
> из `normalized/fullGraph.json`. После любых правок решателя обязательно запускайте
> `npm run build:data`, затем `npm run quality`.

## Пайплайн данных

`data/` — единственный источник истины: файл на линию плюс `transfers.json` и
`layout.json`. Идентификаторы станций выглядят как `1/park-kultury`.

```
data/  →  go-layout-solver  →  normalized/fullGraph.json  →  приложение
```

Редактор замыкает круг: пишет обратно в `data/` и заново запускает решатель.

## Где что лежит

```
data/                схема метро: линии, пересадки, раскладка (источник истины)
go-layout-solver/    решатель на Go: строит граф и геометрию колец
normalized/          производные данные: fullGraph.json, quality_report.json
scripts/             сторожа: редактор не в проде, необъявленные CSS-переменные
scripts/editor/      запись правок редактора в data/ (только dev-сервер)
scripts/quality/     анализатор качества схемы
src/                 приложение (React + Canvas) и модуль метро
public/              иконки, favicon
e2e/                 сквозные тесты пути пользователя (Playwright)
tools/visual-qa/     стенд визуальной приёмки (Docker + Chromium)
docs/                QUALITY.md, VISUAL_QA.md, service-worker.md, metro-reference/
docs/visual-qa/      зафиксированные снимки приёмки
docs/screenshots/    кадры для README
.github/workflows/   CI и ручной деплой
```

Манифест PWA и имя service worker генерируются `vite-plugin-pwa` из секции `manifest`
в `vite.config.ts` — отдельного `.webmanifest` в `public/` нет и заводить его не нужно.

## Рабочие сценарии

**Поменялись данные метро** (`data/**`) или **геометрия колец**
(`go-layout-solver/*.go`):

```bash
npm run build:data && npm run quality
```

Затем визуальная проверка: центр схемы, три кольца, 5–10 крупных узлов.

**Правки в редакторе:**

```bash
npm run dev:editor
```

Карандаш включает режим, внизу появляется панель сохранения. «Сохранить в data/»
(или Ctrl+S) записывает правки прямо в файлы и тут же пересобирает граф. Панель
показывает, что записано, и отдельно — что сохранить нельзя: такие правки остаются
только на экране, и об этом сказано прямо в ней.

Запись работает ТОЛЬКО в dev/editor-режиме: эндпоинт живёт в плагине
`scripts/editor/editorApiPlugin.ts` с `apply: 'serve'` и в сборку не попадает.

**Перед коммитом:**

```bash
npx tsc -b && npm run lint && npx vitest run && npm run build && npm run check:bundle
```

Тот же набор гоняет CI. Если менялась схема, туда же добавляется `npm run quality`
с коммитом обновлённого `normalized/quality_report.json` — CI сверяет отчёт с этой
базовой линией.

## Деплой

Выкатка — общим пайплайном [deploy-kit](https://github.com/tr0llex/deploy-kit): сборка
раскладывается рядом с текущим релизом, симлинк переключается атомарно, версия
сверяется после переключения.

```bash
dk deploy metro       # локально, тем же путём, что и CI
dk rollback metro
```

Описание цели — `.deploy-kit/prod.env`. Конфигурация nginx —
в [deploy-kit/nginx](https://github.com/tr0llex/deploy-kit/tree/main/nginx). Выкатка
намеренно остаётся ручным шагом: у установленного PWA релиз доходит до пользователей
по правилам service worker, а не пайплайна.

## Данные и права

Названия станций, состав линий и времена пересадок соответствуют официальной схеме
московского метро. Геометрия с неё не скопирована: координаты взяты из публичных
референсных данных как затравка, дальше решены и выправлены здесь. Графическое решение
официальной схемы — работа её авторов; проект его не воспроизводит, а рисует
собственную схему по тем же общеизвестным соглашениям.

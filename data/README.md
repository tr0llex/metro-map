# `data/` — схема метро

Единственный источник истины. Всё, что рисуется на схеме и участвует в расчёте
маршрута, лежит здесь и правится руками.

```
data/lines/*.json   линии: станции по порядку, времена перегонов, геокоординаты
data/transfers.json пересадки между линиями + все значения времени по умолчанию
data/layout.json    координаты станций на схеме (правятся редактором)
```

Сборка: `npm run build:data` → `normalized/fullGraph.json` (его читает приложение).

## Почему так

Раньше входом были `new_map_source/metro.ru.csv` (дамп по всем городам России) и
`connections.json`, где пересадки ссылались на станции **текстом** («Библиотека
им.Ленина» на «Арбатско-Покровская линия»). Поверх результата сборки лежал ещё
слой правок `normalized/editor_overrides.json` — координаты, названия, времена.

Из этого следовали три беды. Настоящие данные жили в результате сборки, а не во
входе, поэтому править вход было нельзя. Сопоставление по именам молча теряло
связь при любом расхождении в написании. И одно и то же значение можно было
задать в двух местах, которые расходились при первой правке.

Теперь слой один, связи идут по идентификаторам, а несовпадение идентификатора
останавливает сборку с сообщением, а не выкидывает станцию из схемы.

## Идентификаторы

`<номер линии>/<название латиницей>` — например `1/park-kultury`, `95/moskva-siti`.

Идентификатор станции встречается в трёх файлах, и везде он написан целиком:
искать по нему можно обычным grep. Одноимённые станции на разных линиях
различаются номером линии, поэтому «Парк культуры» на первой и на кольцевой —
это `1/park-kultury` и `5/park-kultury`, две разные станции, связанные пересадкой.

## `lines/*.json`

Имя файла — `<номер линии с ведущими нулями>-<название латиницей>.json`. На
сборку имя не влияет: порядок отрисовки задаётся в коде (кольцевые первыми,
дальше по возрастанию номера), так что переименование файла картинку не изменит.

```jsonc
{
  "id": 1,
  "title": "Сокольническая",
  "color": "#E42313",
  "ring": false,              // true — линия замкнута в кольцо
  "stations": [
    {
      "id": "1/bulvar-rokossovskogo",
      "title": "Бульвар Рокоссовского",
      "lat": 55.814916,        // география: нужна для поиска «рядом со мной»
      "lon": 37.732227,        // на схеме НЕ используется
      "toNextSeconds": 168     // время до СЛЕДУЮЩЕЙ станции в списке
    }
  ]
}
```

Порядок в `stations` — это порядок следования поездов. У последней станции
`toNextSeconds` нет; у кольцевой линии (`"ring": true`) он есть и означает время
до первой станции. Если `toNextSeconds` не указан, берётся
`defaults.rideSeconds` из `transfers.json`.

### Ответвления

Линия не всегда простой путь. У Филёвской ветка на «Москва-Сити» отходит от
«Киевской», а основной ход идёт до «Александровского сада»:

```jsonc
{
  "id": 4,
  "stations": [ /* основной ход */ ],
  "branches": [
    {
      "title": "На Москва-Сити",
      "from": "4/kievskaya",   // станция ЭТОЙ ЖЕ линии, от которой отходит ветка
      "fromSeconds": 180,      // время от неё до первой станции ветки
      "stations": [ /* дальше как обычно */ ]
    }
  ]
}
```

Без этого ветка неизбежно пришивается к последней станции плоского списка, и
маршруты через неё считаются неверно. У кольцевой линии ответвлений быть не может.

## `transfers.json`

```jsonc
{
  "defaults": {
    "rideSeconds": 150,        // перегон, если время не задано явно
    "hubMinSeconds": 240,      // минимум на пересадку внутри узла
    "kindSeconds": { "near": 180, "far": 300, "mcc": 300, "out_of_station": 480 }
  },
  "transfers": [
    { "stations": ["1/park-kultury", "5/park-kultury"], "kind": "near" }
  ]
}
```

`kind` — то, что различает легенда официальной схемы:

| `kind` | что это |
|---|---|
| `near` | переход внутри узла |
| `far` | длинный переход |
| `mcc` | переход на МЦК |
| `out_of_station` | выход в город |

`seconds` можно не указывать — тогда берётся `defaults.kindSeconds[kind]`.
Указывайте только там, где время отличается от типового: иначе в файле не видно
настоящих исключений.

**Пересадочные узлы (хабы) здесь не хранятся.** Узел — это связная компонента
списка пересадок, солвер выводит её сам. Хранить состав узла отдельно значило бы
держать два описания одного факта, которые разъезжаются при первой же правке.
Переходы `out_of_station` в узел не сливаются: это две разные станции, между
которыми надо выйти на улицу.

## `layout.json`

```jsonc
{
  "stations": { "1/park-kultury": [749.658, 966.845] },
  "rings": {}
}
```

Координаты схемы в пикселях. Расставлены руками; правятся редактором
(`npm run dev:editor`, кнопка `OVR` копирует готовый файл в буфер обмена).

Координаты обязаны быть у **каждой** станции, и лишних записей быть не должно —
и то и другое останавливает сборку. Станция без координат просто не нарисуется,
а лишняя запись означает, что станцию переименовали или удалили и забыли про
раскладку.

Пустой `rings` означает, что форма кольцевых линий подбирается автоматически по
координатам станций. Заполненный ключ **жёстко** задаёт форму, и она перестанет
подстраиваться под правки раскладки — редактор пишет его только по явному
подтверждению.

## Что проверяется при сборке

Сборка падает, а не «чинит молча»: дубль идентификатора станции, дубль номера
линии, цвет не в формате `#RRGGBB`, линия короче двух станций, пересадка на
несуществующую станцию, пересадка между станциями одной линии, неизвестный
`kind`, дважды описанная пересадка, неположительное время, ветка от чужой
станции, ответвление у кольцевой линии, станция без координат, координаты
несуществующей станции, форма кольца для некольцевой линии.

## Первые 30 минут в проекте

Так выглядел заход «человека, который не помнит контекста».

**Минуты 0–5. README.** Открыл `README.md`. Заголовок — «Hello Kitty Метро Москва»,
первая строка — «оформленная в стиле Hello Kitty», раздел 9 — «Лицензии у проекта пока
нет из-за использования имени и айдентики Hello Kitty». Пошёл смотреть, где эта
айдентика. Её нет: `index.html` → `<title>Метро Москвы</title>`, в `public/` лежат
`metro-icon.svg` / `metro-icon-maskable.svg`, файлов `public/kitty-metro-icon-*.svg`,
на которые прямо ссылается `docs/LICENSING.md`, не существует. Бренд убран коммитом
`a94c660` «brand: убрать Hello Kitty, ввести собственный знак» — README, LICENSING.md
и ROADMAP об этом не знают. Пять минут потрачены на выяснение, какой из двух
проектов передо мной.

**Минуты 5–8. Запуск.** `npm run dev` — Vite поднялся за **276 мс**. Без нареканий.
`npx vitest run` — **4 с**, 76 тестов в 3 файлах, все зелёные. `npx tsc -b` — **4 с**.
`npm run lint` — **11 с**, чисто (одно предупреждение `baseline-browser-mapping` про
устаревшие данные). `npm run build` — **6 с**, 10 ассетов, PWA-манифест сгенерирован.
Это самая приятная часть проекта: цикл «поправил — увидел» на фронтенде почти мгновенный.

**Минуты 8–12. Данные.** `npm run build:data` — **17 с**. Вывод осмысленный: сколько
времён взято из конфига, какая форма подобрана каждому кольцу с невязкой. Прогнал
второй раз, сравнил с сохранённой копией — `fullGraph.json` побайтово идентичен,
детерминированность реальная, не декларативная.

Дальше начались расхождения. README §3.2 перечисляет семь проходов солвера
(«фильтрация → сборка линий → геометрия колец → снап хабов → раздвижение →

`separation.go` в части холодного старта, `graph.go`) на текущих данных не запускаются.
Про изоляцию мёртвого алгоритма я знал заранее; чего не ожидал — что README продолжает
подробно описывать его как рабочий пайплайн.

Там же: README говорит «Параметры оптимизатора — `normalized/best_params.json`».
`grep` по всему репозиторию: **ноль ссылок**, файл не читает никто, лежит с 2 декабря.

**Минуты 12–16. Качество.** `npm run quality` — **3 с**. Вот это сделано отлично:
таблица по-русски, у каждой метрики значение / цель / вердикт, у проваленных —

Заодно выяснилось, что `ROADMAP.md` устарел целым разделом: пункт P0 №1

**Минуты 16–22. Профилирование 17 секунд.** 17 с на пересборку данных при том, что
основной алгоритм не запускается, выглядело странно. Собрал бинарник отдельно:

**Итог тридцати минут.** Запустить проект — легко и быстро, тут всё в порядке.

## Находки по убыванию боли

### 1. Документация расходится с кодом в проверяемых местах

**Боль.** README, ROADMAP и LICENSING описывают состояние до 4–6 последних коммитов.
Это не «неполнота», а активная дезинформация: вернувшийся человек будет чинить
починенное, крутить параметры, которые никто не читает, и считать себя связанным
лицензионным блокером, которого больше нет.

Проверенный список расхождений:

- Удалить `normalized/best_params.json` и `normalized/layout_metrics.json` вместе с
  упоминаниями. Файл, который никто не читает, в репозитории вреднее отсутствующего:
  он выглядит как ручка управления.
- `docs/LICENSING.md` переписать в одну секцию «блокер снят коммитом `a94c660`,
  осталось переименовать идентификаторы» либо удалить, оставив запись в ROADMAP.
- `docs/VISUAL_QA.md` разрезать на два файла: инструкция по запуску (живёт долго) и
  датированный отчёт (протухает за неделю). Сейчас это один документ, и читатель
  не понимает, какая его половина ещё верна.

### 2. 93% времени сборки данных — одна функция без выключателя

**Боль.** `npm run build:data` = 17 с, из них 21.4 с чистого счёта приходится на
`ApplySeparation` (замер выше; разброс 17–23 с между прогонами). Всё остальное —
чтение CSV, применение оверрайдов, подгонка колец — укладывается в **12 миллисекунд**.

Цикл «поправил время перегона в `travel_times.json` → посмотрел» стоит 17 с, хотя
времена к раскладке отношения не имеют. Цикл «поправил метрику → пересобрал →
померил» стоит 17 + 3 = 20 с. За рабочий день таких итераций десятки.

**Где.** `go-layout-solver/separation.go:100` — `sepIterations = 900`, хардкод;
`relax(sepIterations)` вызывается дважды (строки 1267, 1271). У солвера 7 флагов,
все про пути к файлам, ни одного про режим работы.

**Цена.** 17 с × десятки итераций в день. Плюс скрытая цена: при таком лаге перестаёшь
запускать `build:data` «на всякий случай» и начинаешь коммитить рассинхронизованный
`fullGraph.json`.

**Как решить.** Флаг `-separation-iterations N` (0 = пропустить) и `-fast`, включающий
разумный дешёвый пресет. Правки времён, названий, connections не трогают геометрию —
для них `-separation-iterations 0` даст полсекунды вместо семнадцати. Полный прогон
остаётся дефолтом, чтобы результат в репозитории не поехал.

### 3. Порт раскладки подписей не защищён ничем, кроме комментария

**Боль.** Про сам факт дублирования известно и оно осознанно. Проверил, чем оно
удерживается — и харнесса сверки **не существует**. В репозитории три тест-файла
(`src/metro/fullGraph.test.ts`, `src/metro/routing.test.ts`, `src/routeWorker.test.ts`),
ни один не касается подписей; `grep` по `parity|сверк|харнесс` даёт пусто.

Синхронность держится на комментарии `MetroMap.tsx:347`: «Любая правка алгоритма
ОБЯЗАНА быть внесена в оба места, иначе отчёт о качестве начнёт врать».

Объём: `labelGeom.ts` (368) + `labelLayout.ts` (570) + `render.ts` (250) ≈ **1188 строк**
против соответствующего куска `MetroMap.tsx`. Имена при этом расходятся (`LABEL_W` ↔ `W`,
`LABEL_CANDIDATE_ANGLES` ↔ `CANDIDATE_ANGLES`), так что даже глазами сравнить нелегко.

Отдельный риск: `LABEL_NODE_RADIUS_STATION = 5.564` и `LABEL_NODE_RADIUS_HUB = 9.459`
захардкожены в обоих местах как готовые числа. Они производны от `STATION_RADIUS = 5.2`,
но связь нигде не выражена — правка `STATION_RADIUS` их не подвинет ни в одном из файлов.

**Хорошая новость.** Расхождений сейчас нет. Написал за пять минут 20-строчный
сравниватель (выдёргивает числовые константы из обоих наборов, нормализует префикс
`LABEL_`): **27 общих констант, 0 расхождений**.

**Цена.** Пока ноль. В момент, когда разойдётся, — отчёт о качестве начнёт врать
молча, и заметить это можно будет только по несовпадению картинки с цифрами, то есть
никогда.

**Как решить.** Тот самый сравниватель константами — в `src/metro/labelGeom.test.ts`,
20 строк, добавляется в `npx vitest run` бесплатно. Это не полная сверка алгоритма,
но закрывает самый вероятный класс расхождения (кто-то подкрутил вес и забыл про порт).
Более радикально — вынести чистую геометрию подписей в `src/metro/labelGeom.ts`
и импортировать её обоими потребителями: она не зависит ни от Canvas, ни от React,
единственное настоящее различие — `measureText`, который уже развязан через
`textMetrics.ts`.

### 4. `tsc -b` не покрывает `scripts/` и тесты — CI даёт ложную зелень

**Боль.** Проверено по конфигам и подтверждено запуском:

- `tsconfig.app.json`: `include: ["src"]`, `exclude` — все `*.test.ts` / `*.spec.ts`;
- `tsconfig.node.json`: `include: ["vite.config.ts"]` — ровно один файл.

Итого вне тайпчека: **13 файлов** анализатора качества (`scripts/quality/**`, ~2000 строк),
`scripts/extract_yandex_coords.ts` и **3 тест-файла**. Шаг «Typecheck» в
`.github/workflows/ci.yml` их не видит. Тесты при этом исполняются (esbuild срезает
типы, не проверяя их), так что ошибка типа в тесте не проявится нигде.

Прогнал `scripts/**` отдельным конфигом со `strict` — **чисто, 0 ошибок**. То есть
дыра пока не выстрелила, но она открыта, и именно в той части кода, которая считает
метрики качества схемы.

**Цена.** Сейчас нулевая, потенциально — тихая поломка анализатора, обнаруженная
через недели.

**Как решить.** Третий проект `tsconfig.scripts.json` с `include: ["scripts"]` в
`references` корневого `tsconfig.json`, и убрать `exclude` тестов из `tsconfig.app.json`
(тесты — тоже код, который стоит проверять). Оба изменения бесплатны по времени:
`tsc -b` идёт 4 с.

### 5. ESLint линтит сборку и не линтит `.mjs`

**Боль.** `eslint.config.js` содержит `globalIgnores(['dist', 'dev-dist'])` — без
`dist-editor`. Запросил у ESLint список реально обрабатываемых файлов: из 72 файлов
**11 — это `dist-editor/`**, включая минифицированные `kitty-metro-vendor-*.js`,
`workbox-*.js` и два service worker'а.

Одновременно единственный блок правил ограничен `files: ['**/*.{ts,tsx}']`, поэтому
к `.js`/`.mjs` не применяется **ни одного правила**. `scripts/check-prod-bundle.mjs`,
четыре скрипта `tools/visual-qa/*.mjs` и `public/sw.js` проходят линтер как пустое
место. Именно поэтому мусор из `dist-editor` не даёт ошибок — и именно поэтому
не поймается реальная опечатка в сторожевом скрипте.

**Цена.** 11 с линта, часть из них на артефакты сборки; нулевое покрытие `.mjs`.

**Как решить.** Добавить `dist-editor` (и `dist;C`, см. находку 10) в `globalIgnores`;
завести второй блок `files: ['**/*.{js,mjs}']` с `js.configs.recommended` и
`globals.node`, чтобы скрипты инфраструктуры хотя бы проверялись на неопределённые
переменные.

### 6. Редактор экспортирует поля, которые солвер молча выбрасывает

**Боль.** `src/editor/exportOverrides.ts:220–228` пишет восемь ключей верхнего уровня:
`layout`, `stations`, `lines`, `edges`, `hubs`, `grid`, `ringShapes`, `stationParams`.

Структура `GraphOverrides` в `go-layout-solver/graph_overrides.go:155–164` имеет
шесть полей: `Layout`, `Stations`, `Lines`, `Edges`, `Hubs`, `RingShapes`.
Полей `Grid` и `StationParams` в Go **нет вообще** — `json.Decoder` по умолчанию
игнорирует неизвестные ключи, никакой диагностики не будет.

`theta` (углы станций на кольце) живёт внутри `stationParams`. То есть параметр,
который ROADMAP называет способом задать положение станций на кольце, физически
не может доехать до солвера.

Второй слой той же ловушки: в сегодняшнем `editor_overrides.json` ключа `ringShapes`
**нет**, и кольца подбираются автоматически (`fitBestRingShape`, вывод `build:data`:
`ring line 95: ellipse fit over 31 stations, rms=11.76`). Первый же экспорт из
редактора добавит `ringShapes` — и геометрия колец молча переключится с «подогнано по
станциям» на «жёстко задано вручную». Разница на глаз заметная, причина — неочевидная.

Плюс к этому в `graph_overrides.go` живут комментарии, написанные от лица прошлого
исполнителя: «ТРЕБОВАНИЕ К UI (правка вне моих границ): `canonicalRingShapeFromRingShape`
в `src/components/MetroMap.tsx` должна писать kind "ellipse"...». Это незакрытая задача,
замаскированная под комментарий к типу; в ROADMAP её нет.

**Цена.** Час-два на «почему после экспорта из редактора схема поехала».
Для `theta` — неограниченно, потому что симптом «я задал угол, ничего не изменилось»
не имеет никакого следа в выводе.

**Как решить.**
- В `readGraphOverrides` включить `dec.DisallowUnknownFields()` либо явно перечислить
  игнорируемые ключи и печатать по ним предупреждение: «`stationParams` присутствует в
  оверрайдах, но солвером не читается — 306 записей проигнорировано». Одна строка
  вывода снимает целый класс молчаливых потерь.
- Решить судьбу `stationParams`/`theta`: либо прочитать в Go, либо перестать
  экспортировать из редактора. Сейчас это ручка, не подключённая ни к чему.
- Требования из комментариев в `graph_overrides.go` перенести в ROADMAP.

### 7. `App.tsx` — одна функция на 3200 строк

**Боль.** Файл `src/App.tsx` — 3356 строк, из которых **строки 155–3347 это тело одной
функции `App()`**. Внутри 158 вызовов хуков. Верхнеуровневых объявлений в файле всего
16, и 13 из них — константы.

`src/components/MetroMap.tsx` — 4862 строки, 104 хука, плюс отдельно
`computeStationLabelPlacements` (строки 717–1229, ~500 строк) и сам компонент с 1230-й.

`src/App.css` — 4069 строк. `src/editor/useEditorController.ts` — 1549 строк.

Практические следствия, а не эстетика:

- любое состояние в `App()` перерисовывает всё дерево, потому что мемоизировать
  нечего — компонент один;
- 158 хуков в одном теле означают, что добавление хука в середину — операция с
  риском: порядок хуков нельзя нарушить, а увидеть весь список целиком невозможно;
- поиск по файлу перестаёт работать как навигация: `useEffect` встречается десятки раз,
  и понять, какой из них отвечает за что, можно только чтением подряд.

**Что при этом разделено удачно.** `src/metro/` — образцово: `types.ts` (217),
`graphCore.ts` (254), `routing.ts` (270), `fullGraph.ts` (122), `routingGraphPayload.ts` (115).
Границы проведены по смыслу, файлы читаются целиком, 76 тестов покрывают именно их.
Разбиение редактора на `useEditorController` / `noopEditorController` с переключением
через `EDITOR_ENABLED` — тоже хорошее решение (см. находку «что устроено хорошо»).

**Как решить.** Не переписывать. Вынести из `App()` по одному связному куску за раз,
начиная с самых самостоятельных: работа с `localStorage` (избранное, недавние,
онбординг — 5 ключей, ~150 строк), диплинк и шаринг (`readDeepLinkStationIds`,
`buildRouteShareUrl` уже вынесены наверх, к ним просится остальная логика), жизненный
цикл service worker и баннера обновления. Каждый вынос — отдельный хук в `src/hooks/`,
проверяется существующим `npx vitest run` + `npm run build`.

и вызывать `probe-*.mjs` из `run.sh`, а не из README.

### 9. `quality:check` красный, и это норма

**Боль.** `npm run quality:check` возвращает **exit 1** (проверено): метрика
«Перечёркнутые подписи в центре» — 22.58% при пороге FAIL >20. В CI job `quality`
помечен `continue-on-error: true`, то есть постоянно жёлтый.

Красный сигнал, который всегда красный, перестаёт быть сигналом. Через полгода
невозможно отличить «всё как обычно» от «я только что сломал раскладку»: оба
состояния выглядят одинаково.

**Как решить.** Либо поднять порог FAIL до текущего значения и зафиксировать его как
базовую линию, чтобы job стал блокирующим и падал только на регрессе, либо
сравнивать `quality_report.json` с закоммиченной базовой линией (в `docs/QUALITY.md`
детерминированность заявлена и проверена — сравнение диффом реально работает).
Второй вариант ROADMAP уже предусматривает, он же полезнее.

## Что устроено хорошо и трогать не надо

- **`scripts/quality/**` и `docs/QUALITY.md`.** Лучшая часть проекта. Отчёт за 3 с,
  по-русски, с порогами и поимённым списком виновников — из него сразу получается
  список задач. `docs/QUALITY.md` — единственный документ, который я проверял и в
  котором не нашёл расхождений с кодом: заявленные константы совпадают с
  `MetroMap.tsx`, инвариант `render.movesStations = 0` держится, детерминированность
  подтверждена. Раздел «Чего эта система намеренно не делает» — редкая и очень
  полезная вещь: он экономит спор с самим собой через полгода.

- **`scripts/check-prod-bundle.mjs`.** Проверка факта вместо проверки намерения:
  вырезание редактора держится на сворачивании мёртвой ветки Rollup-ом, и сторож
  ищет в `dist` восемь характерных строк. Отрабатывает за 0 с, сообщение об ошибке
  сразу называет вероятную причину и где смотреть. Образец того, как надо охранять
  хрупкие инварианты.

- **Развязка редактора через `EDITOR_ENABLED`.** `useEditorController` /
  `noopEditorController` с выбором на уровне модуля — редактор не попадает в прод,
  но остаётся полноценным в dev. Механизм хрупкий по природе, но он осознан,
  задокументирован и покрыт сторожем из предыдущего пункта.

- **`scripts/deploy.sh` и `docs/DEPLOY.md` (кроме устаревшего абзаца про workflow).**
  Отказ работать при уже сломанном `nginx -t`, бэкап конфига, атомарная перестановка
  каталогов, `metro.prev` для отката, smoke-проверка соседнего проекта. Для одиночного
  разработчика на общем сервере это ровно та осторожность, которая нужна.
  `--dry-run` честно показывает «менять нечего».

- **`src/metro/`.** Границы модулей проведены по смыслу, файлы 115–270 строк, 76
  тестов идут 4 с. На фоне `App.tsx` видно, что автор умеет разделять — просто до
  UI руки не дошли.

- **`new_map_source/travel_times.json`.** Времена вынесены в конфиг с `$schema` и
  `$readme` внутри файла, солвер печатает, сколько значений взято из конфига и сколько
  ушло на дефолт («293 из конфига, 0 на дефолте»). Подмена модели времени не пройдёт
  незаметно — именно так и надо делать с данными, влияющими на результат.

- **Детерминированность пайплайна.** Проверено: два прогона `build:data` дают побайтово
  идентичный `fullGraph.json`. Это то, на чём вообще возможно сравнение отчётов диффом.

- **Скорость фронтенд-цикла.** dev 276 мс, build 6 с, тесты 4 с, тайпчек 4 с.
  Здесь ничего улучшать не нужно.

- **`tools/visual-qa/run.sh`.** Комментарий про переписывание путей MSYS в аргументах
  Docker и обход этого бага — сохранённые несколько часов отладки для того, кто
  столкнётся с этим на другой машине. Контейнер не ходит на хост вообще, прогон
  одинаков везде.

- **Комментарии в Go, объясняющие «почему», а не «что».** `main.go` про
  взаимоисключающие пути ручной и автоматической раскладки, `rings.go` про то, почему
  форму нельзя подбирать на лету, `graph_overrides.go` про superellipse как псевдоним
  ellipse при n = 2. Это именно тот вид знания, который теряется первым.
